# Звіт з аудиту безпеки Business CRM

**Дата:** 06.11.2026  
**Обсяг:** вихідні архіви Frontend + Backend, локальна Git-історія, конфігурація Netlify/Render/Docker та API-код.  
**Статус:** часткове посилення виконано; production-аудит і повний інтеграційний прогін не виконані.

## Підсумок

У код внесено зміни для посилення сесій, захисту cookie-запитів від CSRF, обмеження частоти запитів, HTTP-заголовків, обробки помилок, завантаження файлів та локального доступу до MongoDB. Основні приватні API-маршрути підключені після `requireAuth`; `/api/health` і публічні `/api/auth/login` та `/api/auth/register` залишаються винятками. Реєстрація створює неактивну заявку, яку має підтвердити власник.

**Це не сертифікація і не гарантія повної безпеки.** Зміни потрібно перевірити на тестовому середовищі, налаштувати секрети та обмеження в хостингу, а потім виконати інтеграційні тести.

## Знайдені проблеми та виправлення

| Рівень | Проблема | Що змінено |
|---|---|---|
| High | JWT мав строк дії 7 днів і не мав механізму відкликання сесій | Строк зменшено до 8 годин; додано `tokenVersion`, перевірку версії під час кожного запиту та відкликання сесій при logout, зміні пароля/ролі або вимкненні користувача |
| High | Cookie-authenticated POST/PATCH/PUT/DELETE не мали перевірки джерела запиту | Додано Origin-перевірку для змінювальних запитів, що використовують cookie; дозволяються лише same-origin, налаштовані `CLIENT_ORIGIN` або локальна розробка |
| Medium | Обмеження brute-force було локальним для email+IP і не мало загального ліміту API | Додано ліміти на API, login (10 спроб/15 хв на IP+email) і register (5/год на IP) |
| Medium | Не було базових security headers і заборони кешування приватних API-відповідей | Додано `nosniff`, `DENY`, Referrer/Permissions/Cross-Origin-Resource-Policy, HSTS у production та `Cache-Control: no-store` для API |
| Medium | JSON body мав ліміт 1 MB | Зменшено до 256 KB |
| Medium | Завантажені файли перевірялися переважно за MIME, який надсилає клієнт, а endpoint віддавав їх inline | Додано перевірку сигнатур основних форматів, обмеження Cloudinary URL, `Content-Disposition: attachment`, `nosniff`, перевірку імені файла та прибирання тимчасового файла після помилки |
| Medium | Локальна MongoDB у Docker була опублікована на всіх мережевих інтерфейсах | Порт прив’язано до `127.0.0.1:27017` |
| Low | Необроблені помилки драйвера могли потрапляти в логи | Прибрано логування повного об'єкта помилки; клієнту повертається загальне повідомлення |
| Low | У middleware Bearer-токенів regex некоректно розпізнавав пробіли | Виправлено розбір заголовка `Authorization` |
| Low | Деякі списки історії/файлів не мали верхньої межі | Обмежено історію зацікавленостей до 500 та список вкладень до 200 записів на запит |

## Перевірки, виконані локально

- Статично перевірено маршрутизацію: усі змонтовані приватні `/api/*` маршрути проходять через `requireAuth`; `/api/users` додатково обмежено роллю owner.
- Переглянуто рольові перевірки `canWrite`/`ownerOnly` та перевірки власника для операцій із продажами.
- Перевірено frontend на використання `localStorage`, `sessionStorage`, `dangerouslySetInnerHTML` та прямого `innerHTML` у `src`: збігів не знайдено.
- Проскановано локальну Git-історію з переданих архівів на типові шаблони секретів. Знайдені збіги відповідали прикладам/змінним середовища; явних реальних ключів у цьому локальному знімку не підтверджено. Віддалений GitHub/інші репозиторії не перевірялися.
- `node --check` пройшов для всіх backend `.js` файлів, `vite.config.js` та service worker.

## Що НЕ було перевірено

- `npm ci`, `npm test`, `npm run build` і `npm audit`: інсталяція залежностей у середовищі аудиту завершувалася timeout, тому результати цих команд відсутні.
- Не виконувалися живі HTTP-тести без авторизації, IDOR, CSRF, brute-force та зміни ролей проти запущеного сервера.
- Не підключалися до реальної MongoDB, Netlify, Render, Cloudinary або DNS. Налаштування production-хостингу не можна підтвердити з архівів.
- Не перевірено фактичні резервні копії, їх шифрування/відновлення, журнали провайдера, TLS-конфігурацію та мережеві ACL бази даних.

## Ризики, що залишилися

1. Rate limiter зберігає лічильники в пам'яті одного Node-процесу. Для кількох інстансів, autoscaling або рестартів потрібен Redis-backed limiter.
2. Доступ до даних у CRM наразі побудований як одна спільна організація, а не multi-tenant із tenant ID. Якщо планується кілька незалежних компаній у спільній БД, потрібна окрема tenant-ізоляція кожного запиту та індексу.
3. Немає окремого повного журналу читання/експорту персональних даних. Поточний audit log охоплює окремі бізнес-операції, але не є повним журналом доступу до PII.
4. DOCX/XLSX перевіряються за ZIP-сигнатурою, але не розпаковуються для повної структурної перевірки/антивірусного сканування. Для високочутливих документів потрібен malware scanning.
5. Вміст текстових файлів перевіряється базово; перевірка сигнатури не замінює антивірус і sandbox.
6. Cloudinary unsigned preset є публічною конфігурацією, а не секретом. Його потрібно обмежити у Cloudinary Dashboard.
7. Історія зацікавленостей обмежена 500 найновішими записами на продукт в одному запиті; повний архівний експорт повинен бути окремим owner-only процесом з аудитом.
8. Локальний Docker MongoDB не має вбудованої автентифікації; порт тепер доступний лише loopback. Не використовуйте цей compose як публічну production-БД.

## Ручні кроки перед production

1. У Render/Backend Hosting встановити `NODE_ENV=production`, `JWT_SECRET` випадковим значенням не менше 32 символів, `MONGODB_URI` із окремим обмеженим DB-користувачем, точний `CLIENT_ORIGIN` та `CROSS_SITE=false` для Netlify proxy.
2. У Netlify встановити `API_PROXY_URL=https://<backend-host>` та перевірити, що HTTPS і proxy працюють. CSP вже додано в `netlify.toml`; після deploy перевірити Console/Network на CSP-помилки й за потреби додати лише необхідні домени.
3. У MongoDB Atlas дозволити мережевий доступ лише з backend egress IP (або іншого контрольованого каналу), використовувати TLS, мінімальні права DB-користувача та автоматичні зашифровані резервні копії. Перевірити відновлення backup.
4. У Cloudinary unsigned preset обмежити дозволені типи (JPEG/PNG/WEBP), максимальний розмір, transformations, папку та правила доступу. Не додавати API secret у frontend.
5. Увімкнути моніторинг 401/403/429/5xx, сповіщення про незвичні входи та ротацію секретів. Не записувати паролі, cookie, JWT або вміст клієнтських записів у логи.
6. Перед використанням реальних даних провести контрольний прогін на staging: unauthenticated API, роль viewer, IDOR на продажах/зацікавленостях/вкладеннях, CSRF з чужого origin, rate limit, upload spoofing, logout/revocation та відновлення backup.
7. Якщо вже були реальні секрети в історії GitHub, вважати їх скомпрометованими: відкликати/ротувати їх у відповідному сервісі. Локальний скан архіву не доводить, що віддалена історія чиста.

## Зміни схеми БД

Додано необов'язкове поле `User.tokenVersion` із default `0` для відкликання сесій. Окрема руйнівна міграція не потрібна; існуючі користувачі трактуються як версія `0`. Після розгортання потрібно перевірити login/logout на staging.
